# LongMemEval — первый 3-рукий замер ПАМЯТИ (none / dump / retrieval)

**Дата:** 2026-06-08 · **Сеттинг:** oracle (только сессии-улики) · **n=80**
стратифицированно (все 6 типов) · **Судья:** gpt-4o-mini · **Харнесс:**
`backend/core/eval/benchmark_longmemeval.py`

## Результат (accuracy)

| Рука | gpt-4o-mini | gemini-3.1-flash-lite |
|---|---|---|
| **A — none** (без памяти) | 0.025 | 0.038 |
| **B — dump** (вся история в контекст) | 0.488 | 0.600 |
| **C — retrieval** (BM25 стенд-ин) | 0.513 | 0.575 |

## Разбивка по типам вопросов (gpt-mini / gemini, рука dump)

| Тип | none | dump | retrieval | Комментарий |
|---|---|---|---|---|
| single-session-user | 0.0 | **0.91 / 0.91** | 0.91 / 0.91 | факт в одной сессии — решено |
| single-session-assistant | 0.0 | 0.75 / **1.0** | 0.75 / 1.0 | решено |
| knowledge-update | 0.0 | **0.79 / 0.90** | 0.84 / 0.90 | обновление факта — решено |

## Что это честно показывает

1. **Память НЕОБХОДИМА — бенчмарк валиден.** Рука none ≈ 0.03 на обеих моделях:
   чистый LLM на персональные факты истории не отвечает. Меряем именно память, не
   параметрику.

2. **Лёгкие типы (одна сессия / обновление) решаются ОБЕИМИ руками** (0.75–1.0).
   Здесь разницы dump vs retrieval нет — факт локален.

3. **Поле боя — multi-session и temporal** (0.19–0.50). Это ровно «увидеть то, что
   размазано по РАЗНЫМ сессиям/встречам» — наш заявленный дифференциатор. И вот
   ключевое: **на multi-session наивный BM25-ретрив НЕНАДЁЖЕН** — у gpt помог
   (0.25→0.31), у gemini ПОВРЕДИЛ (0.50→0.19): BM25 вытащил часть нужных сессий и
   потерял остальные, без которых связка не собирается.

   → **Это измеренный мандат нашей граф-памяти:** идти по СВЯЗЯМ и собрать ВСЕ
   сессии, нужные для многошагового ответа, а не топ-BM25. Именно здесь рука C
   (наш `hybrid_search` + граф) должна бить и dump, и BM25 — а наивный ретрив
   доказал, что просто «похожие куски» тут ломаются.

## Честные оговорки (важно для сравнения с рынком)
- **Сеттинг oracle ≠ опубликованные числа LongMemEval-S.** Oracle даёт только
  сессии-улики (без 50 дистракторов). Поэтому dump здесь высок не потому что модель
  сильна, а потому что мусора нет. Числа Zep ~63.8% / Mem0 49% / ByteRover 92.8% —
  на ПОЛНОМ `_s` (278MB, дистракторы). Прямое сравнение требует прогона `_s`.
- **Рука C — BM25-стенд-ин, НЕ наша память.** Реальный замер нашего дифференциатора =
  заменить `arm_retrieval` на `hybrid_search_orchestrator` + граф (одна строка) в
  среде с зависимостями (в песочнице нет networkx/эмбеддингов).
- Именно на `_s` (дистракторы) проявляется ценность ретрива над dump (lost-in-the-
  middle на длинном контексте) — на oracle это структурно не видно.

## Обновление: добавлена 4-я рука HYBRID (наш алгоритм)

После установки deps (`pip install --user rank_bm25 sentence-transformers`)
добавлена рука **C-real = алгоритм нашего `HybridSearchOrchestrator`** на
per-item: BM25 + sentence-transformer (all-MiniLM-L6-v2) + RRF из нашего же
`backend/core/search/rrf_fusion.py` (k=60, веса BALANCED=1.0/1.0).

**Sanity:** 0/80 fallback на обеих моделях; hybrid отличается от BM25 в 19/80
(gpt) и 14/80 (gemini) — реально гонялся.

### Честный вывод по гибриду
**Гибрид не побеждает BM25 на oracle.** Это **структурное** ограничение, а не
поражение: внутри одного айтема пул кандидатов мал (десятки ходов), BM25 и dense
ранжируют почти одинаково, RRF только усредняет. Реальный выигрыш гибрида
проявляется на больших шумных корпусах (`_s` с 50 дистракторами), не на oracle.

**Открытый сигнал:** gemini-multi-session гибрид +0.062 над BM25 (0.188→0.250) —
именно там, где BM25 раньше «терял часть нужных сессий». Направление наше, но
n=16 в категории — для категориального вывода недостаточно.

### Метод-урок (важнее цифр)
Первый 4-рукий прогон выглядел чистым (hybrid==retrieval = "паритет"), но был
**испорчен тихим fallback в 75/80** (`No module named 'backend'` в `try/except`).
Поймал случайно. Применил вывод к коду — теперь `_load_hybrid()` с явной
проверкой, и зафиксировал общий принцип в `SKILL_DIAGNOSIS.md`: «try/except без
sanity-check = тихая ложь». Без этого отчитался бы паритетом как фактом.

## Следующие шаги (по приоритету)
1. **Прогон `_s` (полный хейстек, 278MB)** — здесь должна проявиться ценность ретрива
   над dump (lost-in-the-middle) и hybrid над BM25 (больше шума → разный recall).
   Это даст числа, прямо сравнимые с Zep ~64–71% / Mem0 49% / ByteRover 92.8%.
2. **Бизнес-бенчмарк** (multi-session подсаженные инсайты) — у графа структурное
   преимущество над per-item ретривом; у конкурентов слоя нет.
3. (Опционально) Полная замена руки C на наш `HybridSearchOrchestrator` через
   Qdrant/Neo4j инфраструктуру — даст за-itemную память с графом и темпоральной
   осью; это уже не алгоритм, а полный продукт.
