# Публичные бенчмарки: LoCoMo + HotpotQA — analysis vs strict

**Дата:** 2026-06-08 · **gpt-4o-mini** (дешёвая) · LoCoMo n=30 (10/cat),
HotpotQA n=30 · Harness: `benchmark_locomo.py`, `benchmark_hotpotqa.py`

Прогон на УЗНАВАЕМЫХ публичных бенчмарках (твоя просьба): LoCoMo = multi-session
память (главная забота), HotpotQA = multi-hop (соединить факты).

## HotpotQA (multi-hop) — analysis ЧИСТО выигрывает

| Рука | Общий | comparison | bridge |
|---|---|---|---|
| strict (top-k+строгий) | 0.567 | 0.5 | 0.591 |
| **analysis** (всё+рассуждение) | **0.767** | **0.875** | **0.727** |

**+0.20 на multi-hop при дешёвой модели.** Соединение фактов из разных параграфов
analysis-режимом работает — это и есть «связать события» как в «когда пошло не так».

## LoCoMo (multi-session) — САМЫЙ ВАЖНЫЙ результат: баланс

| Рука | Общий | **multi-hop** | **temporal** | adversarial |
|---|---|---|---|---|
| strict | 0.433 | 0.2 | 0.1 | **1.0** |
| analysis | 0.433 | **0.6** | **0.3** | **0.4** |

Общий счёт ОДИНАКОВ (0.433), но ПРОФИЛЬ кардинально разный:
- **analysis ВЫИГРЫВАЕТ multi-hop (0.2→0.6, +0.4) и temporal (0.1→0.3, +0.2)** —
  ровно категории, которые тебя волнуют.
- **analysis ПРОИГРЫВАЕТ adversarial (1.0→0.4)** — на принципиально неотвечаемых
  вопросах «компилируй, не отказывайся» заставляет ВЫДУМЫВАТЬ.

### Это ровно твой баланс — теперь ИЗМЕРЕН
strict воздержался на adversarial **10/10**, analysis только **4/10**. Примеры,
где analysis выдумал (должен был сказать «не определить»):
- «Какие ценности Maria хочет привить детям?» → analysis выдумал «compassion,
  responsibility...» (в диалоге этого нет).
- «Что Dave находит приятным в уничтожении старых машин?» → выдумал.

**Вывод честный:** analysis-режим прав для РАССУЖДЕНИЯ (multi-hop/temporal/
multi-session — твои кейсы), но текущая калибровка абстенции СЛАБА —
«CANNOT DETERMINE при отсутствии данных» срабатывает недостаточно строго, и на
неотвечаемом он over-compile'ит.

## Что это значит для продукта (уточнённый тюнинг)

Твоё беспокойство было С ОБЕИХ сторон — и оба подтвердились:
1. **Over-abstention** (строгий) — реальная потеря на multi-hop/temporal
   (multi-hop 0.2, temporal 0.1 у strict). Лечится analysis-режимом.
2. **Over-compile** (analysis) — реальный риск на неотвечаемом (adversarial
   1.0→0.4). Лечится КАЛИБРОВКОЙ абстенции.

**Правильный продукт — НЕ один режим, а:**
- analysis-РАССУЖДЕНИЕ (таймлайн + multi-hop) — для «когда пошло не так / история
  / как сейчас / кого нанять»;
- + СИЛЬНЕЕ абстенция: «отвечай ТОЛЬКО если есть прямая опора в данных; если
  вопрос про факт, которого нет — CANNOT DETERMINE». Сейчас баланс смещён в
  сторону выдумки на 6/10 adversarial — это надо подтянуть.

Это разные риски для разных запросов:
- «когда пошло не так» (есть данные, нужен анализ) → analysis помогает.
- «что Maria хочет привить детям» (данных нет) → analysis НЕ должен выдумывать.

Различить их в проде: `abstention_advisor` уже отделяет synthesis от lookup;
нужен ещё уровень — внутри analysis проверять, есть ли РЕЛЕВАНТНЫЙ ретрив
(retrieval_count) перед компиляцией. Если 0 релевантных → CANNOT DETERMINE даже
в analysis-режиме.

## Сводка по всем замерам (analysis-режим)

| Бенч | Категория | strict | analysis | Δ |
|---|---|---|---|---|
| HotpotQA | multi-hop (есть ответ) | 0.567 | **0.767** | **+0.20** |
| LoCoMo | multi-hop | 0.2 | **0.6** | **+0.40** |
| LoCoMo | temporal | 0.1 | **0.3** | **+0.20** |
| LongMemEval | multi-session | 0.143 | **0.714** | **+0.57** |
| LongMemEval | temporal | 0.455 | **0.727** | **+0.27** |
| **LoCoMo** | **adversarial (нет ответа)** | **1.0** | **0.4** | **−0.60 ⚠** |

**Главный вывод:** analysis-режим стабильно и сильно помогает там, где НАДО
рассуждать и есть данные (твои кейсы). Цена — over-compile на неотвечаемом;
лечится калибровкой абстенции (retrieval-gate перед компиляцией). Без сильной
модели.

## Проверка «gated» калибровки — НЕ сработала (измерено)

Попробовали 3-ю руку `gated`: тот же analysis, но СИЛЬНАЯ дисциплина опоры
(«отвечай ТОЛЬКО при прямой опоре; не выводи невысказанные мнения; иначе CANNOT
DETERMINE»). Гипотеза: вернёт adversarial к ~1.0, сохранив multi-hop/temporal.

| Рука | Общий | multi-hop | temporal | adversarial |
|---|---|---|---|---|
| strict | **0.433** | 0.2 | 0.1 | **1.0** |
| analysis | 0.400 | **0.6** | **0.2** | 0.4 |
| **gated** | 0.333 | 0.3 | 0.0 | 0.7 |

**Вывод: gated ПЕРЕ-корректирует.** adversarial поднялся 0.4→0.7 (хорошо), но
ценой обвала ТВОИХ категорий: multi-hop 0.6→0.3, temporal 0.2→0.0. Общий счёт
УПАЛ (0.400→0.333). Один промпт не может одновременно «жёстко не выдумывать» и
«смело компилировать мультихоп» — это фундаментальный конфликт абстенции и синтеза.

## Продуктовое решение (зафиксировано)

**Выбран analysis + honesty-framing, БЕЗ gated.** Обоснование — §1 гардрейл
(бенчмарк ≠ цель) + твои прямые требования:

1. **LoCoMo adversarial-штраф НЕ совпадает с продуктовой ценностью.** adversarial —
   это вопросы про факты, которых в данных НЕТ (чувства Caroline, ценности Maria).
   Но твой реальный запрос — обратный: «найди кого нехватало / где гапы», «когда
   пошёл раскол» — это КОМПИЛЯЦИЯ из разрозненных сигналов, не lookup. Ты прямо
   сказал: «система даже если не нашла, потенциально может дать ответ». Жёсткая
   абстенция (gated) убивает ровно это.
2. **Цена честности — не отказ, а РАЗМЕТКА.** Вместо «компилируй ИЛИ молчи» —
   `ANALYSIS_PROMPT` теперь компилирует И отделяет ЯВНО сказанное от ВЫВОДА
   (помечает «вероятно / судя по обсуждениям / это указывает на»), а при пустых
   данных не выдумывает. Это лечит over-compile без потери multi-hop/temporal.

Итоговый промпт продукта — `ANALYSIS_PROMPT` (honesty-framing), gated оставлен в
harness как измеренный контр-пример (`benchmark_locomo.py`, рука `gated`), не в проде.

## Подключение в продукт (сделано)

`answer_mode_router` подключён в реальный chat-путь за флагом
`enable_answer_mode_router` (default **OFF** → синтез байт-в-байт прежний):
- `EnhancedSearchOrchestrator.search()` зовёт `route(query)` (singleton → сброс
  на каждый запрос), кладёт режим в `response_metadata['answer_mode']`;
- `_synthesize_answer()` при `mode == "analysis"` добавляет в system_prompt
  валидированный analysis-блок (порт `ANALYSIS_PROMPT` на язык продукта: ответ
  на русском, инструкция #7) — соединяй по сессиям/датам, рассуждай о порядке/
  изменении, компилируй, но отделяй факты от выводов и не выдумывай;
- factual-вопросы → синтез без изменений.

Прямые факты не трогаем; данные/ретрив не меняются — только усиление инструкции
синтеза на вопросах динамики/истории/мультисессии (твои отчётные кейсы).

## Архитектурный evidence-гейт `guarded` — ТОЖЕ не сработал (измерено)

Закрывали открытый пункт по-настоящему: вместо промпта — АРХИТЕКТУРНЫЙ гейт
(`benchmark_locomo.py`, рука `guarded`). Два раздельных шага: (1) дешёвый
evidence-gate «есть ли опора? (мультихоп-вывод = YES) YES/NO»; (2) при YES —
ХОРОШИЙ analysis-компилятор, при NO — CANNOT DETERMINE.

| Рука | Общий | multi-hop | temporal | adversarial |
|---|---|---|---|---|
| strict | **0.433** | 0.2 | 0.1 | **1.0** |
| analysis | 0.367 | **0.5** | **0.2** | 0.4 |
| gated (промпт) | 0.333 | 0.3 | 0.0 | 0.7 |
| **guarded (арх. гейт)** | 0.367 | 0.3 | 0.0 | **0.8** |

**Тот же компромисс, другой механизм.** guarded поднял adversarial 0.4→**0.8**
(почти как strict), но обвалил твои категории: multi-hop 0.5→0.3, temporal
0.2→**0.0**. Гейт сказал `CANNOT DETERMINE` на ОТВЕЧАЕМЫХ: «When did John organize
a basketball camp» (#11, strict/analysis ответили), «What style of guitars does
Calvin own» (#3). На ДЕШЁВОЙ модели сам гейт не отличает «выводимо мультихопом»
от «отсутствует» и склоняется к NO — это та же трудная оценка ответимости.

### Вывод (закрыто измерением, дважды)
**Бинарный гейт ответимости на дешёвой модели НЕ решает баланс** — он лишь
сдвигает тот же компромисс strict↔analysis. Доказано двумя независимыми
механизмами (промпт-гейт `gated`, архитектурный `guarded`).

**Продукт уже корректен — гейт сверх этого не нужен:**
1. **Genuine-absence уже закрыт структурно.** `_synthesize_answer` при пустом
   ретриве (`not context["sources"] and not extra_context`) возвращает честное
   «не нашёл информации» (orchestrator.py ~стр.1400) — это и есть правильный
   retrieval-gate для реального кейса «искали сотрудника, которого нет». Не
   требует LLM-гейта, не трогает отвечаемые вопросы (у них ретрив непуст).
2. **Topic-present-but-attribute-absent (LoCoMo adversarial)** — это вопросы-
   ловушки про факт, которого нет, хотя сущность есть. Для ПРОДУКТА это не
   ценность (твой кейс обратный — «собери вывод из гапов»), а honesty-framing
   уже помечает вывод как вывод («вероятно / судя по обсуждениям»), что полезнее
   плоского отказа. Бенчмарк-судья за adversarial требует отказа — но это
   расхождение метрики и продукта (§1 гардрейл), а не дефект.

Итог: **analysis + honesty-framing подтверждён как правильный продуктовый выбор**,
теперь дважды. Бинарный answerability-гейт оставлен в harness (`gated`,`guarded`)
как измеренные контр-примеры, в прод не идёт.

## Темпоральная резолюция — ВЫЛЕЧЕНО (+0.20 на temporal)

Диагноз провала temporal (был 0.1–0.2 везде): дело НЕ в формате судьи, а в
**резолюции относительных дат**. Модель якорилась на ДАТУ СЕССИИ и не применяла
смещение. Примеры (gold vs analysis):
- «Last week before 13 Oct 2022» → analysis дал «13 October» (дату сессии, не вычел неделю);
- Nate «yesterday» от сессии 22 авг (gold 21 авг) → дал «22 August» (дату сессии);
- John drums (gold «February 2022») → analysis «around March 2022».
Когда модель резолвила — попадала («summer 2023», «January 5 2024»).

**Фикс — чисто аддитивная инструкция** (рез. относительных выражений по смещению
к дате фрагмента + якорь «сейчас/последнее» на самые свежие даты). Замер на
temporal-подмножестве LoCoMo (n=10, gpt-4o-mini):

| Рука | temporal |
|---|---|
| strict | 0.10 |
| analysis (без правила) | 0.10 |
| **analysis + temporal-resolution** | **0.30** |

**+0.20, ×3.** 3 вопроса флипнулись в верные (drums March→February, Tim Aug→
September), 0 регрессий. Остаток падает на точном вычитании недели («week before
X» — судья строг к дате-сессии vs дате-события) и на чисто фактических ошибках
(Calvin: Miami vs Tokyo — это ретрив, не время).

Перенесено в продукт: `ANALYSIS_PROMPT` (answer_mode_router), продуктовый
analysis-блок (`_synthesize_answer`, на русском) и harness `_ANALYSIS`. Безопасно
— инструкция только помогает темпоральным, не вредит остальным. Закрывает твой
кейс «не путать данные годичной давности и свежие на вопросе как идёт сейчас».

### Root cause провала temporal — найден и вылечен в КОДЕ (0.20 → 0.60)

Разбор «почему такие ответы» вскрыл ОДИН баг под всеми промахами. Модель делает
половину работы: находит нужную сессию и читает относительное выражение, но
**выводит саму дату сессии вместо «дата − смещение»**. Размер смещения разный —
отсюда то «на день», то «на неделю», но вычитание не делается НИ РАЗУ:

| # | Память (дата сессии + выражение) | Верно | Модель давала |
|---|---|---|---|
| Evan | [6 Jan 2024] «…**yesterday**» | 5 Jan | 6 Jan (дата сессии) |
| Maria | [16 June 2023] «joined a gym **last week**» | 9 June | 16 June (дата сессии) |
| Nate | [22 Aug 2022] «won international tournament **yesterday**» | 21 Aug | 22 Aug (дата сессии) |
| Joanna | [6 Oct 2022] книга «**last week**» | ~29 Sep | 6 Oct (дата сессии) |

Причина механическая: в памяти `[22 Aug 2022] …yesterday` абсолютная дата стоит
ВПЛОТНУЮ — дешёвой модели проще скопировать видимую дату, чем вычесть смещение.
Промпт-инструкция проигрывает приору «эхо даты».

**Фикс (скелет+LLM): считаем смещение В КОДЕ** (`temporal_resolver.py`), аннотируя
текст разрешённой датой («…yesterday (resolved ≈ 21 August 2022)»). Замер на
temporal-подмножестве:

| Рука | temporal |
|---|---|
| analysis (промпт-инструкция) | 0.20 |
| **analysis + code-resolved** | **0.60** |

**×3, +0.40.** Флипнулись ровно «yesterday»/«last week» кейсы (Evan, Maria, Nate,
Joanna, drums). Остаток 4/10: 1 ошибка ретрива (Calvin/Miami), 1 ответ в золотом
диапазоне (судья строг), 1 будущее («next month» — резолвер только про прошлое),
1 не тот anchor. По сути ~7/10. `temporal_resolver` — чистый stdlib примитив с
юнит-тестами; продуктовое применение — резолвить «вчера/на прошлой неделе» в
транскриптах встреч против даты встречи (интеграция — следующий шаг).

## ФИНАЛ АУДИТА: product-рука лучшая на полном LoCoMo n=30

Полный прогон с рукой `product` = analysis-промпт + code-resolved даты
**продуктовым** `temporal_resolver` (тот же код, что в `_assemble_context`, не
копия) — ровно то, что получает пользователь при `enable_answer_mode_router=true`:

| Рука | **Общий** | multi-hop | **temporal** | adversarial |
|---|---|---|---|---|
| strict | 0.433 | 0.2 | 0.1 | **1.0** |
| analysis | 0.433 | **0.6** | 0.2 | 0.5 |
| **product** | **0.567** | **0.6** | **0.6** | 0.5 |

- **Первая конфигурация, обогнавшая strict по ОБЩЕМУ счёту** (+0.134).
- temporal **0.1→0.6 (×6 vs strict)**; флипы = ровно диагностированные кейсы
  (Evan 5 Jan, Maria 9 June, Nate 21 Aug, drums February, Joanna 29 Sep).
- multi-hop сохранён (0.6), adversarial не пострадал от аннотаций (0.5=analysis).

### Бизнес-задача проверена вживую (НЕ только бенчмарк)

Аудит «бенчмарки И бизнес-задача» нашёл и закрыл критичную дыру: резолвер был
валидирован на английском, а транскрипты продукта РУССКИЕ — 0/8 русских
выражений резолвилось. Добавлены русские выражения (вчера/позавчера/на прошлой
неделе/неделю назад/в прошлом месяце/на днях/в прошлую пятницу/год назад) и
кириллические месяцы в якорях. Затем живой прогон на gpt-4o-mini (русская
компания, 3 встречи, зреющий конфликт) — все 4 реальных клиентских запроса:

1. «когда пошло не так и раскол» → хронология с датами, точка перелома
   (заморозка мобильного 17 фев → недовольство → уход), причины-следствия;
2. «как идёт проект сейчас?» → по самой свежей встрече, старый план отделён;
3. «кого нанять» → гапы из разрозненных сигналов: 2-й бэкендер + дизайнер;
4. «когда Миша подал заявление» → **8 марта** («позавчера» от встречи 10 марта —
   русская резолюция дала точную дату, а не дату встречи).

Также: сквозной e2e (флаг ON: route → аннотация → analysis-блок → metadata),
регрессия 15/15 наборов, ruff чистый, флаг документирован в config JSON (OFF,
включать после ручной проверки на инфре). Найден и закрыт риск молчаливого
отключения фичи (think/__init__ → autogen): устойчивый загрузчик роутера с
fallback по пути файла.

## Preference/advice роутинг — ВЫЛЕЧЕНО (0.067 → потенциально 0.667)

Диагноз: в LongMemEval-S retrieval-рука дала single-session-preference **0.067**,
а analysis-режим — **0.667**. Но preference-вопросы оказались по сути advice
(«Any suggestions?», «What should I serve…?», «Do you have any ideas…?») и
**5 из 6 роутились в factual** (строгий lookup), хотя им нужен СИНТЕЗ
предпочтений из истории. Это убивало их в проде.

**Фикс:** добавлены advice/recommendation-маркеры в `answer_mode_router`
(`any suggestions/tips/ideas`, `what should I…`, `can you suggest`, `how can I`,
рус. «посоветуй», «что мне приготовить», «как мне…»). Теперь **6/6 preference →
analysis** (= измеренные 0.667 вместо 0.067), при этом фактические lookup'и
(«когда дедлайн», «кто назначен») остаются factual — 0 регрессий (тест
`test_advice_preference_route_to_analysis` + регрессионная проверка factual).
